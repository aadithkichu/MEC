# Compiler Design Lab — Viva Notes

## 1. LEX — Strings Not Containing a Specific Substring

### 1.1 What is lexical analysis?

**Lexical analysis** is the first phase of a compiler.

It takes the source program as a sequence of characters and groups them into meaningful units called **tokens**.

Example:

```c
int count = 10;
```

The lexer can produce:

```text
int       → keyword
count     → identifier
=         → operator
10        → number
;         → separator
```

### Token vs Pattern vs Lexeme

These three are commonly asked in viva.

**Token:** A category/class of lexical units.

Example:

```text
IDENTIFIER
NUMBER
KEYWORD
OPERATOR
```

**Pattern:** The rule describing what a token looks like.

Example:

```text
[a-zA-Z][a-zA-Z0-9]*
```

describes an identifier.

**Lexeme:** The actual character sequence found in the source program.

For:

```c
count = 10;
```

`count` is the **lexeme**, `IDENTIFIER` is its **token**, and

```text
[a-zA-Z][a-zA-Z0-9]*
```

is its **pattern**.

---

## 1.2 What is LEX?

**LEX** is a tool used to generate a **lexical analyzer/scanner**.

We provide:

```text
Regular expressions + actions
```

and LEX generates C code containing the scanner.

Traditionally:

```bash
lex program.l
```

produces:

```text
lex.yy.c
```

Then:

```bash
gcc lex.yy.c -ll -o program
```

produces the executable.

---

## 1.3 Structure of a LEX program

A LEX file has **three sections**:

```c
definitions
%%
rules
%%
user subroutines
```

For example:

```c
%{
#include <stdio.h>
%}

%%
[0-9]+      { printf("Number"); }
[a-zA-Z]+   { printf("Word"); }
%%

int yywrap()
{
    return 1;
}
```

### Section 1 — Definitions

Between:

```c
%{
...
%}
```

we place C declarations, headers, variables, etc.

Example:

```c
%{
#include <stdio.h>
%}
```

### Section 2 — Rules

Between the two `%%` symbols:

```c
%%
pattern     action
%%
```

Example:

```c
[0-9]+      { printf("Number"); }
```

The pattern is:

```text
[0-9]+
```

and the action is:

```c
{ printf("Number"); }
```

### Section 3 — User subroutines

After the second `%%`, we write C functions.

Example:

```c
int yywrap()
{
    return 1;
}
```

---

# 1.4 Regular expressions in LEX

LEX uses regular expressions to describe patterns.

### `.` — Any character

```text
.
```

matches almost any single character except newline.

### `*` — Zero or more

```text
a*
```

matches:

```text
""
"a"
"aa"
"aaa"
...
```

### `+` — One or more

```text
a+
```

matches:

```text
"a"
"aa"
"aaa"
```

but not the empty string.

### `?` — Zero or one

```text
a?
```

matches either:

```text
""
"a"
```

### Character class

```text
[abc]
```

matches one of:

```text
a
b
c
```

### Range

```text
[a-z]
```

matches any lowercase letter.

```text
[0-9]
```

matches any digit.

### Negation/complement

```text
[^0-9]
```

means any character **except a digit**.

Similarly:

```text
[^a-zA-Z]
```

means anything except an alphabetic character.

### Concatenation

```text
ab
```

means `a` followed by `b`.

### Alternation

```text
a|b
```

means either `a` or `b`.

---

# 1.5 Matching a substring

Suppose the first four characters of the name are:

```text
CHAT
```

and we want to reject strings containing `CHAT`.

A simple LEX pattern is:

```text
.*CHAT.*
```

Meaning:

```text
.*       → anything before CHAT
CHAT     → required substring
.*       → anything after CHAT
```

Therefore:

```text
MYCHATPROGRAM
```

matches.

But:

```text
HELLOWORLD
```

doesn't.

### Important viva point

LEX does **not** normally need to manually scan every character here. The regular expression describes the pattern and the generated scanner performs the matching.

---

# 1.6 LEX matching priority

LEX follows two important rules.

### Rule 1 — Longest match

LEX chooses the rule that matches the **longest possible input**.

This is called the **maximal munch** principle.

### Rule 2 — Earlier rule wins

If two rules match the same length, the rule appearing **earlier** in the LEX file is selected.

Example:

```c
"if"        { printf("Keyword"); }
[a-z]+      { printf("Identifier"); }
```

For:

```text
if
```

both can potentially match the same length.

The first rule wins, so it is recognized as a keyword.

---

# 1.7 Important LEX variables

### `yylex()`

`yylex()` is the main lexical analyzer function generated by LEX.

It reads input and identifies tokens.

When using LEX alone:

```c
yylex();
```

starts lexical analysis.

When using LEX + YACC:

```text
yyparse()
   ↓
yylex()
   ↓
token
   ↓
yyparse()
```

The parser requests tokens from the lexer.

---

### `yytext`

`yytext` contains the **currently matched lexeme**.

Example:

```c
[a-zA-Z]+
{
    printf("%s", yytext);
}
```

If the input is:

```text
hello
```

then:

```text
yytext = "hello"
```

---

### `yyleng`

`yyleng` contains the **length of the current lexeme**.

If:

```text
yytext = "hello"
```

then:

```text
yyleng = 5
```

---

### `yywrap()`

`yywrap()` is called when the lexer reaches the end of the input.

A common definition is:

```c
int yywrap()
{
    return 1;
}
```

Returning `1` tells LEX that there is no more input.

# 2. YACC — Valid Variable / Identifier

## 2.1 What is YACC?

**YACC** stands for:

> Yet Another Compiler Compiler

It is a parser generator.

LEX handles:

```text
characters → tokens
```

YACC handles:

```text
tokens → grammatical structure
```

So:

```text
Input
 ↓
LEX
 ↓
Tokens
 ↓
YACC
 ↓
Parse / Syntax decision
```

---

# 2.2 What is a CFG?

**CFG = Context-Free Grammar**

A CFG describes the syntax of a language using production rules.

A grammar consists of:

1. Terminals
2. Non-terminals
3. Production rules
4. Start symbol

---

## 2.3 Terminals

Terminals are symbols that appear in the actual input.

For an identifier grammar:

```text
LETTER
DIGIT
```

can be terminals/tokens supplied by the lexer.

For example:

```text
a
1
+
```

can ultimately correspond to terminals.

---

## 2.4 Non-terminals

Non-terminals are grammar variables used to describe structures.

Example:

```text
variable
```

is a non-terminal.

---

## 2.5 Production rule

A production specifies how a non-terminal can be formed.

Example:

```text
variable → LETTER
variable → variable LETTER
variable → variable DIGIT
```

This means a variable:

* starts with a letter
* can then contain letters
* can then contain digits

---

## 2.6 Start symbol

The start symbol is the top-level grammar symbol.

Example:

```text
start → variable '\n'
```

Here:

```text
start
```

is the start symbol.

---

# 2.7 Identifier grammar

The required rule is:

> A variable starts with a letter followed by zero or more letters/digits.

Conceptually:

```text
variable → LETTER
         | variable LETTER
         | variable DIGIT
```

Examples accepted:

```text
a
abc
a1
abc123
x9
```

Examples rejected:

```text
123
1abc
```

because the first character must be a letter.

---

# 2.8 LEX and YACC interaction

This is a **very important viva question**.

LEX recognizes the input:

```text
abc123
```

and produces tokens such as:

```text
LETTER LETTER LETTER DIGIT DIGIT DIGIT
```

YACC receives these tokens and checks whether they satisfy the grammar.

Flow:

```text
Source input
     ↓
   LEX
     ↓
 Tokens
     ↓
   YACC
     ↓
Grammar checking
     ↓
Valid / Invalid
```

---

# 2.9 `%token`

In YACC:

```c
%token LETTER DIGIT
```

declares token names.

The lexer returns them:

```c
[a-zA-Z]    { return LETTER; }
[0-9]       { return DIGIT; }
```

The parser uses:

```text
LETTER
DIGIT
```

in its grammar.

---

# 2.10 `yylval`

`yylval` is used to pass a **semantic value** from LEX to YACC.

For example:

```c
[0-9]+
{
    yylval = atoi(yytext);
    return NUMBER;
}
```

Here:

```text
yytext
```

contains the string representation, while:

```text
yylval
```

contains its numerical value.

For example:

```text
Input: 123

yytext = "123"
yylval = 123
token = NUMBER
```

For more complex types, YACC can use:

```c
%union
```

Example:

```c
%union
{
    int value;
    char *str;
}
```

---

# 2.11 `yyparse()`

`yyparse()` is the parser function generated by YACC.

Usually:

```c
int main()
{
    yyparse();
}
```

starts syntax analysis.

During parsing, YACC calls:

```c
yylex()
```

to obtain tokens.

---

# 2.12 `yyerror()`

`yyerror()` is called when a syntax error occurs.

Example:

```c
void yyerror(char *s)
{
    printf("Invalid Variable\n");
}
```

If the input violates the grammar, this function is called.

---

# 2.13 Top-down vs bottom-up parsing

### Top-down parsing

Starts from the start symbol and tries to derive the input.

Example:

```text
S
↓
AB
↓
...
```

It constructs the parse from the root toward the leaves.

Examples include:

* Recursive descent
* LL parsing

### Bottom-up parsing

Starts from the input and tries to reduce it back to the start symbol.

```text
input
 ↓
tokens
 ↓
reduce
 ↓
...
 ↓
start symbol
```

YACC generates **bottom-up parsers**, traditionally based on **LALR(1)** parsing.

This is an important viva answer:

> **YACC is primarily a bottom-up parser generator.**

# 3. CALCULATOR — LEX + YACC

This experiment combines lexical analysis, parsing, precedence, associativity, and semantic actions.

---

# 3.1 Basic architecture

```text
Expression
    ↓
   LEX
    ↓
NUMBER + NUMBER * NUMBER
    ↓
   YACC
    ↓
Parsing
    ↓
Semantic actions
    ↓
Result
```

For:

```text
10+20*2
```

the expected result is:

```text
50
```

because multiplication has higher precedence.

---

# 3.2 Operator precedence

Consider:

```text
10 + 20 * 2
```

There are two possibilities:

```text
(10 + 20) * 2 = 60
```

or:

```text
10 + (20 * 2) = 50
```

Normal arithmetic requires:

```text
* and / > + and -
```

Therefore:

```text
10 + (20 * 2)
```

is selected.

---

# 3.3 `%left`

In YACC:

```c
%left '+' '-'
%left '*' '/'
```

declares operators as left associative.

The later declaration has **higher precedence**.

Therefore:

```text
%left '+' '-'
%left '*' '/'
```

means:

```text
* /   → higher precedence
+ -   → lower precedence
```

---

# 3.4 Associativity

Associativity determines how operators of the same precedence are grouped.

For:

```text
10 - 5 - 2
```

subtraction is left associative:

```text
(10 - 5) - 2
```

giving:

```text
3
```

not:

```text
10 - (5 - 2)
```

---

## `%left`

Used for left-associative operators:

```c
%left '+' '-'
```

Example:

```text
a-b-c
```

becomes:

```text
(a-b)-c
```

---

## `%right`

Used for right-associative operators.

For example, assignment is usually right associative:

```text
a = b = c
```

can be interpreted as:

```text
a = (b = c)
```

---

## `%nonassoc`

Used when an operator should **not** be allowed to associate with itself.

For example, some grammars may use it for comparison operators to reject expressions such as:

```text
a < b < c
```

---

# 3.5 Semantic actions

YACC allows C code to be executed when a grammar rule is reduced.

Example:

```c
expression:
      expression '+' expression
      {
          $$ = $1 + $3;
      }
```

Here:

### `$1`

Semantic value of the first symbol.

### `$2`

Semantic value of the second symbol.

For:

```text
expression '+' expression
```

`$2` corresponds to:

```text
+
```

### `$3`

Semantic value of the third symbol.

### `$$`

Semantic value of the left-hand side.

Therefore:

```c
$$ = $1 + $3;
```

means:

> Calculate the value of the two expressions and store their sum as the value of the resulting expression.

---

# 3.6 Attribute evaluation

Semantic values are called **attributes**.

For:

```text
10 + 20
```

the parser can calculate:

```text
10 → attribute = 10
20 → attribute = 20
+  → operation
```

Then:

```text
$$ = 10 + 20
```

giving:

```text
30
```

This is an example of **syntax-directed translation**.

---

# 3.7 Shift-reduce parsing

YACC uses bottom-up parsing.

The parser maintains a stack and performs operations such as:

### Shift

Move the next input token onto the stack.

Example:

```text
NUMBER
```

is shifted onto the stack.

### Reduce

Replace a sequence on the stack with a non-terminal according to a grammar rule.

Example:

```text
NUMBER
```

can reduce to:

```text
expression
```

### Accept

The complete input satisfies the grammar.

The parser accepts.

### Error

The input cannot be parsed according to the grammar.

`yyerror()` is invoked.

---

# 3.8 Shift/Reduce conflict

A **shift/reduce conflict** occurs when the parser cannot immediately decide whether to:

```text
SHIFT
```

the next token or:

```text
REDUCE
```

using an existing grammar rule.

Arithmetic expressions commonly produce such ambiguity.

For example:

```text
E → E + E
E → E * E
```

with:

```text
E + E * E
```

The parser needs to know whether to reduce or continue shifting.

Operator precedence solves this.

```c
%left '+' '-'
%left '*' '/'
```

---

# 3.9 Reduce/Reduce conflict

A **reduce/reduce conflict** occurs when the parser has two possible grammar rules that can both be reduced.

Example conceptually:

```text
A → x
B → x
```

If the parser sees `x`, it may not know whether to reduce it to `A` or `B`.

Reduce/reduce conflicts are generally more serious than shift/reduce conflicts and usually indicate an ambiguous or poorly designed grammar.

---

# 3.10 How to avoid conflicts

Use:

* Correct grammar design
* Operator precedence
* Associativity
* `%left`
* `%right`
* `%nonassoc`

For arithmetic:

```c
%left '+' '-'
%left '*' '/'
```

is enough for the basic calculator.

# 4. ABSTRACT SYNTAX TREE — AST

This is probably the most concept-heavy experiment.

---

# 4.1 What is an AST?

**AST = Abstract Syntax Tree**

It is a tree representation of the essential structure of a program or expression.

For:

```text
a + b * c
```

the AST is:

```text
      +
     / \
    a   *
       / \
      b   c
```

Notice that `*` is below `+`.

Therefore:

```text
a + (b*c)
```

is represented naturally.

---

# 4.2 Parse tree vs AST

### Parse tree

A parse tree contains the complete grammar structure.

It may contain:

* Non-terminals
* Terminals
* Parentheses
* Grammar-specific intermediate nodes

### AST

An AST removes unnecessary syntactic details and keeps the important structure.

For example:

```text
(a+b)
```

The parentheses are important for parsing but don't necessarily need to become a node in the AST.

So ASTs are generally **smaller and more useful for later compiler phases**.

---

# 4.3 Example

Expression:

```text
a+b*c-d
```

AST:

```text
          -
         / \
        +   d
       / \
      a   *
         / \
        b   c
```

Preorder traversal:

```text
- + a * b c d
```

Postorder traversal:

```text
a b c * + d -
```

---

# 4.4 Why AST is useful

The AST can be used by later compiler stages for:

* Semantic analysis
* Type checking
* Intermediate code generation
* Optimization
* Code generation

For example:

```text
a+b*c
```

can be converted into intermediate instructions such as:

```text
t1 = b * c
t2 = a + t1
```

The AST makes this structure easy to process.

---

# 4.5 Syntax Directed Translation

**Syntax Directed Translation (SDT)** associates actions with grammar productions.

For example:

```c
E:
    E '+' T
    {
        $$ = createNode("+", $1, $3);
    }
```

When the parser reduces:

```text
E + T
```

it creates an AST node:

```text
+
```

with:

```text
left  = $1
right = $3
```

So parsing and AST construction happen together.

---

# 4.6 SDD vs SDT

### Syntax Directed Definition — SDD

An SDD associates **attributes** with grammar symbols and semantic rules with productions.

Example concept:

```text
E → E1 + T

E.val = E1.val + T.val
```

### Syntax Directed Translation — SDT

SDT places semantic actions directly inside the grammar.

Example YACC:

```c
E:
    E '+' T
    {
        $$ = $1 + $3;
    }
```

So the key distinction is:

> **SDD describes attributes and semantic rules; SDT embeds actions into the grammar.**

---

# 4.7 S-attributed definitions

An SDD is **S-attributed** if it uses only **synthesized attributes**.

A synthesized attribute is calculated from the children and passed upward.

Example:

```text
        +
       / \
      E   T
```

The value of `+` can be calculated from the values of its children.

```text
E.val = E1.val + T.val
```

The information flows:

```text
children
   ↑
parent
```

This is particularly convenient for bottom-up parsing and YACC.

---

# 4.8 L-attributed definitions

An **L-attributed definition** allows inherited attributes as well, subject to restrictions.

Information can flow from:

* parent → child
* left sibling → right sibling

Hence the name **L-attributed**.

A simple conceptual view:

```text
       Parent
       /    \
      A      B
             ↑
       information from A
```

L-attributed definitions are useful for certain left-to-right translations.

### Viva distinction

**S-attributed:**

```text
Only synthesized attributes
```

**L-attributed:**

```text
Synthesized + restricted inherited attributes
```

---

# 4.9 AST data structure in C

A common AST node structure is:

```c
struct node
{
    char data[20];
    struct node *left;
    struct node *right;
};
```

Each node contains:

```text
data
left child
right child
```

For:

```text
a+b
```

the root contains:

```text
+
```

and has:

```text
left  → a
right → b
```

---

# 4.10 `malloc()`

Nodes are created dynamically using:

```c
malloc()
```

Example:

```c
struct node *newnode;

newnode = (struct node *)malloc(sizeof(struct node));
```

`malloc()` allocates memory dynamically.

This is useful because we don't know beforehand how many AST nodes will be required.

---

# 4.11 Creating an AST node

Example:

```c
createNode("+", left, right);
```

can create:

```text
       +
      / \
   left right
```

A typical function is:

```c
struct node *createNode(char *data,
                        struct node *left,
                        struct node *right)
{
    struct node *newnode;

    newnode = (struct node *)malloc(sizeof(struct node));

    strcpy(newnode->data, data);

    newnode->left = left;
    newnode->right = right;

    return newnode;
}
```

---

# 4.12 AST construction during reduction

This is an important viva question.

Suppose grammar has:

```c
E:
    E '+' T
    {
        $$ = createNode("+", $1, $3);
    }
```

When the parser reduces:

```text
E + T
```

it creates a new `+` node.

The already-created trees:

```text
$1
$3
```

become its children.

So:

```text
       +
      / \
    $1   $3
```

is produced.

This process continues until the complete AST is created.

# 5. C `FOR` LOOP — YACC Syntax Checking

## 5.1 What is syntax checking?

Syntax checking verifies whether an input follows the grammar of a language.

For example:

```c
for(i=0;i<10;i++)
```

has the basic structure:

```text
for
(
initialization
;
condition
;
increment
)
```

---

# 5.2 Three major parts of a `for` loop

A C `for` loop has:

### 1. Initialization

Example:

```c
i = 0
```

Executed before the loop begins.

### 2. Condition

Example:

```c
i < 10
```

Determines whether another iteration occurs.

### 3. Increment/decrement

Example:

```c
i++
```

or:

```c
i--
```

Executed after an iteration.

Therefore:

```c
for(i=0;i<10;i++)
```

can be divided into:

```text
initialization → i=0
condition      → i<10
increment      → i++
```

---

# 5.3 Basic grammar

Conceptually:

```text
forstmt → FOR '(' init ';' condition ';' increment ')'
```

Then:

```text
init → ID '=' expr
```

```text
condition → expr relop expr
```

```text
increment → ID INC
          | ID DEC
          | ID '=' expr
```

---

# 5.4 Optional components

In actual C, the three expressions of a `for` statement can be omitted.

For example:

```c
for(;;)
```

is syntactically valid.

That means the grammar needs an **empty production**.

For example:

```text
init → ID '=' expr
     | ε
```

where:

```text
ε
```

means an empty string.

Similarly:

```text
condition → expr relop expr
          | ε
```

and:

```text
increment → ID INC
          | ID DEC
          | ID '=' expr
          | ε
```

Then:

```c
for(;;)
```

can be accepted.

### Important

If your lab program only checks:

```c
for(i=0;i<10;i++)
```

and doesn't include empty productions, it is checking a **restricted subset** of C `for` syntax.

---

# 5.5 Lexer tokens for `for`

The lexer can recognize:

```c
"for"       { return FOR; }
```

Then:

```text
for
```

becomes:

```text
FOR
```

Similarly:

```c
"++"        { return INC; }
"--"        { return DEC; }
```

recognize increment/decrement.

---

# 5.6 Relational operators

The lexer can define:

```c
"<="        { return LE; }
">="        { return GE; }
"=="        { return EQ; }
"!="        { return NE; }
```

Then YACC can use:

```text
LE
GE
EQ
NE
```

in its grammar.

Single-character operators can be returned directly:

```text
<
>
```

For example:

```c
relop:
      '<'
    | '>'
    | LE
    | GE
    | EQ
    | NE
```

---

# 5.7 Why return tokens for `++` and `--`?

Because:

```text
++
```

is a multi-character operator.

The lexer can recognize it as one token:

```text
INC
```

instead of returning two separate:

```text
+
+
```

This makes the grammar simpler.

---

# 5.8 Separators

Important separators in a `for` statement are:

```text
(
)
;
```

For:

```c
for(i=0;i<10;i++)
```

the token sequence is approximately:

```text
FOR
(
ID
=
NUM
;
ID
<
NUM
;
ID
INC
)
```

YACC checks whether this sequence matches its grammar.

---

# 5.9 Syntax error

Consider:

```c
for(i=0 i<10;i++)
```

The first semicolon is missing.

The parser expects:

```text
;
```

but encounters:

```text
ID
```

Therefore a syntax error occurs and:

```c
yyerror()
```

is called.

Example:

```c
void yyerror(char *s)
{
    printf("Invalid FOR Statement\n");
}
```

---

# 5.10 Error recovery in YACC

YACC provides an `error` token that can be used to recover from syntax errors.

Example:

```c
statement:
      expression
    | error ';'
      {
          printf("Syntax error recovered\n");
      }
```

The parser can discard input until it reaches a suitable synchronization token, such as:

```text
;
```

This allows parsing to continue instead of immediately terminating.

For a simple lab program, however, you may only implement:

```c
void yyerror(char *s)
{
    printf("Invalid FOR Statement\n");
}
```

without advanced recovery.

# 9. Common Viva Questions — Quick Answers

### What is a compiler?

A compiler translates a source program written in a high-level language into an equivalent target program, often machine or intermediate code.

### What is lexical analysis?

The first compiler phase that converts a character stream into tokens.

### What is a parser?

A component that checks whether the sequence of tokens follows the grammar of the language.

### What is LEX?

A lexical analyzer generator.

### What is YACC?

A parser generator that traditionally generates LALR(1) bottom-up parsers.

### What is a token?

A symbolic category representing a class of lexemes.

### What is a lexeme?

The actual character sequence corresponding to a token.

### What is a pattern?

The rule describing the form of a lexeme.

### What does `yytext` contain?

The currently matched lexeme.

### What does `yyleng` contain?

The length of the current lexeme.

### What does `yylex()` do?

It scans input and returns tokens.

### What does `yyparse()` do?

It parses tokens according to the grammar.

### What does `yyerror()` do?

It reports syntax errors.

### What is `yylval`?

It carries semantic information from LEX to YACC.

### Is YACC top-down or bottom-up?

**Bottom-up.**

### What parsing technique does YACC traditionally use?

**LALR(1).**

### What is shift?

Putting the next input token onto the parser stack.

### What is reduce?

Replacing a sequence of symbols by the corresponding grammar non-terminal.

### What is accept?

The parser has successfully recognized the complete input.

### What is a shift/reduce conflict?

When the parser cannot decide whether to shift the next token or reduce using a grammar rule.

### What is a reduce/reduce conflict?

When two different grammar rules could both be reduced.

### Which is generally more serious?

A **reduce/reduce conflict** is generally more problematic because the grammar provides two competing reductions.

### What does `%left` do?

Specifies left associativity and contributes precedence information.

### What does `%right` do?

Specifies right associativity.

### What does `%nonassoc` do?

Prevents chaining of operators at that precedence level.

### What is an AST?

A condensed tree representation of the essential syntactic structure of a program.

### Difference between parse tree and AST?

A parse tree represents the complete grammar derivation; an AST removes unnecessary syntactic details and retains the essential structure.

### Why use `malloc()` for AST nodes?

Because the number of nodes is determined dynamically while parsing.

### What is an S-attributed definition?

An attribute definition using only synthesized attributes.

### What is an L-attributed definition?

An attribute definition allowing synthesized attributes and restricted inherited attributes.

### What is syntax-directed translation?

Translation where semantic actions/attribute computations are associated with grammar productions.

### What are `$1`, `$2`, `$3`?

Semantic values of the first, second, and third RHS symbols.

### What is `$$`?

The semantic value of the left-hand side non-terminal.

### Why is `*` given higher precedence than `+`?

To correctly implement standard arithmetic grouping:

```text
a + b * c
```

→

```text
a + (b*c)
```

### What are the three parts of a C `for` loop?

```text
initialization
condition
increment/decrement
```

### What is `ε`?

The empty string/empty production.

### Why use `INC` for `++`?

To represent the complete multi-character operator as one parser token.
